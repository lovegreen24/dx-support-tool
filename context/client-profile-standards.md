## このドキュメントについて

このファイルは、中小企業DX伴走支援ツールにおける「クライアントカルテに記録すべき項目」「ヒアリング必須項目の構造」「DX成熟度診断の4領域とスコア項目」「6承認ポイントの固定順序」「機密情報の取り扱い」の**単一の真実源**を定義する共通コンテキストである。上記の依存エージェントは、作業開始時に必ずこのファイルを読み込み、ここに定義されたデータ構造・順序・注意事項に沿って自らの入出力（クライアント登録・決算書解析結果・ヒアリング回答・補助金マッチング結果・DX成熟度スコア・提言書ドラフト・案件進捗記録）を扱う。

なお、財務分析（`analyze_working_capital` / `compare_cost_benchmark` の分析の切り口）は本ファイルの依存対象外であり、`context/consulting-standards.md` を参照する。

このファイルを変更した場合、依存エージェント7つすべてに矛盾が生じないか点検すること（単一性の原則）。データ構造の正式な定義元は `docs/requirements.md`（§3 ツール/MCP定義リスト T-001〜T-012、§4 データ設計概要）および `docs/SCOPE_PROGRESS.md`（データモデル定義、6承認ポイントの固定順序）であり、本ファイルはそれらを個別エージェントが参照しやすい形に整理したものである。矛盾が生じた場合は要件定義書側を正とする。

## 1. クライアントカルテの必須項目

対象MCP: `save_client_record`（T-001・クライアント新規登録）

クライアントカルテは、財務系MCPのクラウドDB（cloud_proxy）を単一の真実源として保存する。クライアント管理エージェントは、初回ヒアリング（訪問メモ）から以下の必須項目を漏れなく聞き取り、登録前に不足がないか確認する。

| 項目 | 型 | 説明 | 必須 |
|---|---|---|---|
| client_id | string | `save_client_record` 実行時にMCP側が発行する一意識別子。以降すべてのMCP呼び出し（決算書解析・ヒアリング登録・分析・提言書生成・案件進捗）でクライアントを紐付けるキーとして使う | 発行後は必須（登録時は未確定） |
| name | string | 企業名（正式名称） | 必須 |
| industry | string | 業種（`compare_cost_benchmark` の業種別ベンチマーク照合、`assess_digital_maturity` の優先度判定に使う） | 必須 |
| employee_count | number | 従業員数（補助金マッチングの対象条件照合、業種別目安値の解釈に使う） | 必須 |
| fiscal_year_end | string(月/日 または月) | 決算期。決算書解析・財務分析のタイミング判断に使う | 必須 |

### 1-1 登録時の確認ルール

- 上記5項目のいずれかが未確定のまま `save_client_record` を実行しない。不足があれば追加ヒアリングで埋めてから登録する（潔癖性の原則：不完全なデータをフォールバック値で埋めない）。
- `client_id` はMCP発行後に不変のキーとして扱う。他のエンティティ（財務データ・ヒアリング回答・DX成熟度診断結果・案件進捗）はすべて `client_id` で紐付けて参照する。
- 例（ある卸売業クライアントの場合）: 訪問メモに「従業員数はおおよそ20名前後」としか記載がない場合、概算のまま登録せず、正確な人数を確認してから `save_client_record` を実行する。

## 2. ヒアリング項目のカテゴリ構造

対象MCP: `register_hearing_answer`（T-003）／`remind_missing_hearing_items`（T-004）

ヒアリング回答は `client_id, category, question_id, answer` の形式でクラウドDBに保存する（上書き可）。ヒアリング管理エージェントは以下の構造を前提に回答を登録・管理する。

| フィールド | 型 | 説明 |
|---|---|---|
| client_id | string | 対象クライアントのID |
| category | string | ヒアリング項目の分類（例: 財務・業務フロー・DX成熟度・経営課題 等、業種横断で共通の分類軸を使う） |
| question_id | string | カテゴリ内の質問を一意に識別するID |
| answer | string/json | 回答内容（自由記述・選択式いずれもここに格納） |

### 2-1 未回答チェックのルール

- `remind_missing_hearing_items` はカテゴリ×question_id の組み合わせで、まだ `register_hearing_answer` が登録されていない項目を検出する。ヒアリング管理エージェントは、未回答項目をカテゴリ単位でまとめて提示し、フォローアップの抜け漏れをゼロに近づける（成功指標③に対応）。
- `generate_proposal_draft`（T-007）はヒアリング全問完了が前提であるため、未回答が残っている状態で提言書生成に進まない。
- 回答の上書きは、訪問回数を重ねて情報が更新された場合に許容する。ただし上書き前の内容を消す形になるため、重要な変更（数値の大幅な訂正等）はカルテ上に更新履歴が追える形で扱う。

## 3. DX成熟度診断の4領域とスコアフィールド

対象MCP: `assess_digital_maturity`（T-012）

診断対象は以下の4領域とする（`docs/requirements.md` T-012・CLAUDE.mdのMCP構成に準拠）。各領域の評価観点の詳細（成熟度レベル定義・優先度判定ロジック）は `context/consulting-standards.md` §2 を参照すること。本ファイルでは、DX成熟度診断結果を保存するデータ構造のみを定義する。

| 領域 | 主な評価観点 |
|---|---|
| 営業 | SFA/CRMの活用、EC・オンライン販路の活用 |
| 総務経理 | クラウド会計の導入、電子帳簿保存法への対応 |
| 労務 | 年末調整・社会保険手続きの電子化、勤怠管理システムの活用 |
| 社内基盤 | チャット・Web会議ツールの活用、RPA導入、電子契約の活用 |

### 3-1 保存スキーマ — `digital_maturity_assessments`（M-012側DB、`docs/SCOPE_PROGRESS.md` データモデル定義準拠）

| フィールド | 型 | 説明 |
|---|---|---|
| client_id | string | クライアントID（財務系MCP発行のIDを共通利用） |
| assessed_at | datetime | 診断実施日時 |
| sales_score | number | 営業領域（SFA/CRM・EC活用）スコア |
| admin_score | number | 総務経理領域（クラウド会計・電子帳簿保存法）スコア |
| hr_score | number | 労務領域（年末調整/社保電子化・勤怠管理）スコア |
| infra_score | number | 社内基盤領域（チャット/Web会議/RPA/電子契約）スコア |
| overall_score | number | 総合スコア |
| priority_improvements | json | 改善優先度リスト |
| raw_answers | json | 構造化ヒアリング回答の原本 |

### 3-2 運用ルール

- DX成熟度診断エージェントは、診断のたびに `raw_answers` を必ず保存する（後から評価ロジックを見直した際に再スコアリングできるよう、原本を残す。刹那性の原則の例外＝生データは資産として保持する）。
- `priority_improvements` は4領域すべてを並列に並べず、`context/consulting-standards.md` §2-2 の優先度判定ロジックに従って絞り込んだ結果を格納する。
- `client_id` は §1 のクライアントカルテと同一キーを使い、財務系MCPのクラウドDBとは別DB（M-012側）に保存されるが、参照時は `client_id` で必ず突き合わせられるようにする。

## 4. 6承認ポイントの固定順序

対象MCP: 案件管理MCP（T-010）

案件進捗管理エージェントは、Googleスプレッドシートの案件進捗シート（`case_id, client_id, client_name, step_1_status〜step_6_status, step_1_approved_at〜step_6_approved_at, updated_at`）に対し、以下の固定順序で承認ポイントを記録する。この順序はフロントエンドの型 `ApprovalStep` および進捗ダッシュボードの表示順序と一致させること（`docs/SCOPE_PROGRESS.md` データモデル定義に準拠）。

| # | 承認ポイント | 対応するMCP/工程 |
|---|---|---|
| ① | クライアント登録 | `save_client_record`（T-001） |
| ② | 決算書解析 | `parse_financial_statement`（T-002） |
| ③ | ヒアリング回収 | `register_hearing_answer` 全問完了（T-003・T-004で未回答ゼロを確認） |
| ④ | 財務分析 | `analyze_working_capital`（T-005） |
| ⑤ | ベンチマーク比較 | `compare_cost_benchmark`（T-006） |
| ⑥ | 提案書生成 | `generate_proposal_draft`（T-007） |

### 4-1 運用ルール

- 各ステップのステータスは `completed` / `active` / `pending` の3値のみを使う。フロントエンドの `ApprovalStep` 型と語彙を一致させ、独自の値（例: `done`, `in_progress` 等）を追加しない（単一性の原則）。
- ステップは順序を飛ばして `completed` にしない。前段（例: ②決算書解析が未完了の状態で④財務分析が完了）が発生した場合は、実データの不整合として案件進捗管理エージェントが検知し、握り潰さずに報告する。
- `step_N_approved_at` は、実際にコンサルタント本人が当該ステップの内容を確認・承認したタイミングで記録する。MCP呼び出しが成功しただけで自動的に承認済みとしない（承認は人間の最終判断が前提）。

## 5. 機密情報の取り扱い

`docs/requirements.md` §5 セキュリティ要件に準拠する。

- クライアントの財務データ・経営課題情報は**機密情報**として扱い、外部漏洩を防止する。決算書解析結果・ヒアリング回答・DX成熟度診断結果・提言書ドラフトのいずれも、この機密情報に含まれる。
- 依存エージェントは、成果物（提言書ドラフト・分析結果の要約等）を生成する際、機密情報を必要以上に外部（本ツールの管轄外のサービス・チャネル）へ出力・転記しない。
- 進捗ダッシュボードは簡易パスワード保護（マイ専用のためシンプルな認証で十分）だが、そこに表示される情報（クライアント一覧・ヒアリング完了率・提案書ステータス・承認履歴）も機密情報の一部であるという前提で扱う。
- 補助金マッチングエージェントがNotionの補助金台帳と照合する際も、クライアント側の機密情報（財務数値・経営課題の詳細）をNotion側に書き込まない。参照は一方向（Notion→ツール側）とする。

## 6. 固有名の扱い（汎用性維持）

このファイル、および本ファイルを参照する各エージェントの成果物は、特定のクライアント企業に固定化されない**汎用ロジック**として設計する。

- 本文（地の文）に実在・仮想を問わずクライアント固有の社名・個人名・具体的業種名を直接書き込まない。
- 業種や事例に触れる必要がある場合は、必ず「例（ある〇〇業クライアントの場合）」のように**ラベル内でのみ**用いる。ラベルの外（データ構造・ルールそのものを述べる文）には固有名を出さない。
- これにより、コンサルタントが担当するどのクライアントに対しても、同じカルテ構造・ヒアリング構造・承認順序をそのまま適用できる状態を保つ。

## 7. 精度向上について（注記）

本ドキュメントは `docs/requirements.md`（§3・§4・§5）および `docs/SCOPE_PROGRESS.md`（データモデル定義・6承認ポイントの固定順序）に記載された正式なデータ設計をそのまま整理したものであり、新たな推測・収集は行っていない。要件定義書・進捗ダッシュボード側のデータ構造が変更された場合は、本ファイルおよび依存エージェント7つを同時に点検・更新すること（単一性の原則）。
